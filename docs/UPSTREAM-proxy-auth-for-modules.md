# Upstream request: offer `X-Infratak-Proxy-Auth` to module vhosts

**For:** `takwerx/infra-TAK` · **Raised by:** ATLAS (TAK-MDM) module ·
**Relates to:** the change your source labels `v10.1.1 S1`

---

## The ask, in one line

The Caddyfile generator injects `X-Infratak-Proxy-Auth` for the console's own
upstream. Please make the same injection available to module vhosts, so a module
can verify that a request carrying `X-Authentik-*` really came through Caddy.

---

## Why

A module behind a forward-auth vhost reads the administrator's identity from the
headers Caddy sets:

```python
username = request.headers.get("x-authentik-username")
groups   = request.headers.get("x-authentik-groups")
```

Nothing in those headers proves they came from Caddy. Anything able to open a
socket to the module's loopback port is an administrator by sending two headers.

This is the finding you already fixed for the console. From
`generate_caddyfile`:

```python
# v10.1.1 S1: attach the proxy-auth secret AFTER forward_auth, on the same
# matcher — so it is present exactly when forward_auth passed … The console
# requires it alongside X-Authentik-Username once the gate is armed, so a
# forged identity header alone is dead even if the client strip above ever
# regresses on a future plain-proxy path.
```

The design is right, and the comment states the threat precisely. The request is
only that modules can opt into it.

## What modules get today

Every vhost, module vhosts included, already receives the **strip**:

```caddy
request_header -X-Infratak-Proxy-Auth
```

so a client cannot forge the header. What module vhosts do not receive is the
**injection** — that is emitted only alongside `reverse_proxy 127.0.0.1:5001`.

The result is a half-present mechanism: a module is protected against a forged
proxy-auth header, and has nothing to verify. The strip is the harder half and
it is already done.

## Why a module cannot solve this itself

- The vhost is generated by core; a module calls `ctx['generate_caddyfile']`
  and does not author the Caddy config.
- The secret lives in `.config/proxy_auth.json`, which a module has no
  contract to read.
- A module inventing a second secret would mean a second mechanism doing the
  same job, diverging from the one you already maintain.

ATLAS has shipped what it can from its own side — a peer-address restriction
(`TAKMDM_TRUSTED_PROXIES`) written by its module at deploy. ⚠️ **It is not
sufficient, and cannot be.** Caddy runs on the host and reaches the container
through the bridge gateway; so does every other process on that host. The peer
address cannot separate them. It closes accidental exposure and leaves
host-local forgery untouched.

## Suggested shape

Whatever fits your generator. Two that would work:

**A. Opt-in per module vhost.** A module declares it, and the generator emits
the same two lines it already emits for the console:

```python
register_module({
    'key': 'atlas',
    'proxy_auth': True,      # inject X-Infratak-Proxy-Auth on authenticated requests
    ...
})
```

**B. On by default for forward-auth vhosts.** Any vhost that gets
`forward_auth` also gets the injection. Safe for modules that ignore the header,
immediately useful for those that check it, and needs no module-side declaration
at all.

**B is the better default**, for the reason your own comment gives: a module that
ignores the header is no worse off, and one that checks it is no longer relying
on network placement alone.

## What the module would do with it

Require it alongside the identity header, and fail closed when present-and-wrong:

```python
if expected_secret and not hmac.compare_digest(
    request.headers.get("x-infratak-proxy-auth", ""), expected_secret
):
    raise HTTPException(403, "not reached through the proxy")
```

Reading the secret needs a supported path — a `ctx` accessor, or the module's
deploy step receiving it to write into its own env, whichever you prefer.

## Discovered by

A security audit of ATLAS, published in its repository as `SEC_AUDIT.md`
(finding **S-1**). ⚠️ The audit's first version overstated the exposure — it
claimed neighbouring containers could reach the module's port, and measurement
disproved that. The corrected finding stands at **High**: full administrative
control, reachable by anything with code execution on the host or by a
configuration error that republishes the port.

No response needed on any timeline; ATLAS is not blocked. Raising it because the
mechanism already exists, the gap is one conditional in the generator, and every
module behind forward auth has the same hole.
